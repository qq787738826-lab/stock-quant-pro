# 智能体团队架构决策

本文件冻结跨阶段决策。更改这些决策必须单独评审，不能作为普通实现细节顺带修改。

## 权威与边界

1. **Java 权威**：Java 唯一生成 taskId 和六个 runId，负责状态、幂等、缓存、持久化和跨语言结果校验。
2. **Python 无状态**：Python 只分析 Java 提供的只读 contextSnapshot，不访问任务数据库，不保存状态，不改写 Java 身份。
3. **六智能体固定名单**：只包含 DATA_QUALITY、MARKET_REGIME、TECHNICAL_ANALYSIS、STRATEGY_BACKTEST、ANNOUNCEMENT_RISK、POSITION_RISK。
4. **总控不是 agentRun**：不得创建 `CHIEF_DECISION` run；总控结果只进入 `agent_decisions`。

## 风险、证据与决策

5. **POSITION_RISK 唯一正式否决权**：其他智能体不得声明或创建正式 veto。
6. **DATA_QUALITY 只负责门禁阻断**：`BLOCKED` 不是正式否决，DATA_QUALITY 的 `veto` 必须为 false。
7. **证据优先于自然语言结论**：finding 和 veto 必须引用真实、完整、唯一的 evidence；不得编造证据。
8. **规则评分与 LLM 解释分离**：可审计规则产生结构化评分和决策；未来 LLM 最多作为解释层，不得成为权威计算或证据来源。

## 演进与治理

9. **先本地 PostgreSQL，后外部数据源**：优先复用已有数据表建立只读上下文，再评估外部数据源。
10. **先规则能力，后 LLM**：先完成可复现、可测试的本地规则能力，再单独评估模型解释层。
11. **不自动交易**：智能体输出仅用于研究和模拟，不直接修改现金、持仓、成交或控制券商客户端。
12. **大阶段隔离**：每个大阶段使用独立任务分支、完整测试、ChatGPT 实际提交验收和用户 merge 批准，不跨大阶段偷渡功能；同一大阶段的内部工作包不分别提交或验收。
13. **单一事实来源**：`docs/agent-team/CURRENT_STATE.md` 是进度、能力边界和下一阶段入口的唯一权威状态文件。

## 证券状态事件物化

14. **稳定证券身份必须显式映射**：跨来源证券身份必须通过 `security_identity_registry` 与 `source_security_identity_mappings` 的显式关系解析；`sourceInstrumentId` 缺失时不得物化事件。mappingLogicalKey 只使用稳定业务字段，mapping append-only 且 TEST/DEMO 隔离，mappingAssuranceLevel 参与 event assurance 保守传播；同 key 不同 identity 必须 conflict。symbol、名称、代码前缀、board 或 exchange 均不得被用来自动合并或修复身份。
15. **active 表示上市资格而非当日可交易性**：`active` 表示证券仍具有目标市场上市与 Universe 资格。普通停牌、临时停牌、无成交或缺 bar 不改变 `active`；`active=true` 必须满足 `listed=true`，退市结果必须为 `listed=false, active=false`。
16. **V1 事件转换不可放宽**：`SECURITY_STATUS_EVENT_V1` 继续复用现有完整 `resultingState` 和七类事件转换语义。初始链只能使用 `FULL_STATUS_SNAPSHOT`；增量事件只能改变冻结目标字段；多字段、身份或局部 valid 更正不得拆成多个 V1 事件。
17. **raw、attempt、result 与 event 基数固定**：一条 raw revision 可以被多个 run 处理；每个 run/raw 可有连续的多个 terminal attempt，每个 attempt 恰好一个 result，每个 result 引用零或一个 event。相同 eventLogicalKey 全局最多一个 event 和一条 lineage；result 唯一边界是 attempt，不得错误地对 raw 建立全局唯一。AttemptStatus 与 normalization outcome 必须精确映射，`REJECTED` 不得替代 identity、contract 或 conflict 终态。
18. **V6 event 主表保持唯一权威**：`security_status_events` 是唯一证券状态 event 主表；eventContractVersion 必须持久化，来源 revision 唯一键必须包含 recordNamespace。同一 namespace、securityLogicalKey、contract 最多一个 FULL 根，非根必须引用同链 predecessor，且一个 predecessor 最多一个后继；direct SQL 不能构造双根或跨 namespace、identity、contract 链。业务 Hash 禁止使用数据库物理 ID。
19. **Event lineage 与 Manifest V2 独立版本化**：每个首次物化的逻辑 event 恰好一条 append-only raw→event lineage；复用 event 只新增本次 normalization result。`INGESTION_MANIFEST_V2_SECURITY_EVENT` 在 run 创建时冻结，覆盖该 run 全部 attempt/result；accepted/rejected 只取每条 raw 的最大连续 attemptNo，历史失败仍进入 manifest 但不重复计数。不能修改 `INGESTION_MANIFEST_V1` 既有编码或在封存时切换版本。
20. **事件时间与原子性**：event `knownAt` 必须等于 terminal attempt 的 `derivedKnownFrom`，effective、published、observed、recorded 与 known 时间不得混用，`completedAt` 不进入业务 manifest。event、首次 lineage、attempt 与 normalization result 必须在数据库事务中原子提交，并由唯一约束、不可变 trigger 和锁共同保护。

上述决策的完整字段、outcome、并发与验收契约见 [stage-2d2b1b-security-event-materialization-design.md](stage-2d2b1b-security-event-materialization-design.md)。它们只批准 TEST/DEMO 边界，不解除 FORMAL/PIT 门禁；2D-2B-1B-1 的实际完成状态继续以 [CURRENT_STATE.md](CURRENT_STATE.md) 为准。

## 阶段开发治理

21. **权威文档职责固定**：根目录 [AGENTS.md](../../AGENTS.md) 约束开发执行和安全；`CURRENT_STATE.md` 是当前进度、能力、阻断和入口的唯一事实来源；本文件冻结跨阶段决策；`ROADMAP.md` 只定义方向、顺序、依赖和验收门槛。`PROGRESS_LOG.md` 只能索引已经完成、已经验收或已经合入的历史里程碑及其提交、测试、ChatGPT 验收与用户 merge 批准证据，不得记录活动状态、当前阻断、当前入口、下一阶段或当前工作任务。`tasks/` 只保存大阶段或其内部工作包的任务边界。二者都不得成为平行状态权威。
22. **双窗口开发模式**：ChatGPT 窗口规划较大的完整开发阶段，定义架构、范围、边界和验收标准，并在 Codex 推送后基于实际 Git commit、完整 diff 和测试证据验收；Codex 开发窗口在一个任务分支连续完成该大阶段全部内部工作包，自主实现、测试、修复、commit 和普通 push，但不得 merge 或自行进入下一大阶段。用户只需对高风险业务选择和重大方案分歧作出最终选择，并最终批准 merge，不需要逐文件批准或批准普通 commit/push。详细执行规则以 [AGENTS.md](../../AGENTS.md) 为准。
23. **实际提交验收**：Codex 的聊天汇报、未提交工作区和自审不能代替最终验收。ChatGPT 必须检查已推送任务分支的实际 commit SHA、完整提交差异、测试证据、阶段边界和权威文档一致性，并向用户报告通过或不通过；不通过时由同一 Codex 开发窗口继续修复并提交推送。项目不固定设置第三个独立 Codex Review 窗口。
24. **大阶段连续交付**：路线图不构成自动开发授权。每次授权一个较大的完整开发阶段，大阶段可包含多个内部工作包；内部工作包不分别开发、Review、提交或验收，Codex 应连续完成，最终形成大阶段任务分支提交。ChatGPT 验收通过后由用户批准 merge；合并后 Codex 停止，ChatGPT 才规划下一大阶段。
25. **自主修复与高风险暂停**：普通编译错误、测试失败、局部重构、文件数量、常规实现选择和文档一致性问题由 Codex 在已授权大阶段内自主解决。仅当核心架构存在重大方案分歧、数据库核心模型或不可逆迁移、Java/Python 公共契约的重大选择、无法证明可消除的前视偏差、真实交易/下单/资金风险，或必须由用户选择的高风险业务规则时暂停。暂停报告必须说明原因、影响、方案、兼容性和迁移风险及所需选择；没有相应选择或新授权不得继续高风险实施。
26. **Canonical Hash 契约先于依赖实现**：任何大阶段新增会被持久化、进入公共契约或承担数据版本含义的领域 Hash 前，必须先在该大阶段架构中冻结版本化 canonical 契约。未冻结的算法、编码、Unicode、字段白名单、排序、空值、时间、精度、数据版本、跨语言和兼容策略不得由 Codex 猜测；如果形成重大公共契约、数据库模型或不可逆迁移选择，按第 25 条暂停。契约未冻结前不得实现依赖它的生产 Hash、迁移或公共契约。2F 内部工作包的具体门禁见 [tasks/2f0-backtest-context-foundation.md](tasks/2f0-backtest-context-foundation.md)。
27. **Knowledge-time 证据独立于业务日期与内容 Hash**：`trade_date<=requestTradeDate` 只证明业务日期上界，不证明该值在历史决策时点已经可知；内容 Hash 只证明给定内容稳定，也不证明历史可得性。可靠回测输入必须把决策时间、`knowledgeCutoff`、首次观察、来源/修订、快照或数据集版本、迟到与覆盖、公司行动和复权变化纳入可审计契约；无法证明 knowledge-time 合法性时 `backtestContext` 必须保持 `available=false`。2F 获准采用的不可变观察、PIT 模型、`known_at` 与 V9 迁移边界由下列决定冻结。

## 可靠回测与 STRATEGY_BACKTEST

28. **V9 本地 PIT 日线观察模型**：V9 新增 append-only `market_data_observation_batches` 与 `daily_bar_observations`，`daily_bars` 继续只是当前态兼容投影。观察批次和日线版本禁止 `UPDATE`、`DELETE`、`TRUNCATE`；同一来源、证券、交易日的 QFQ 内容和 revision 与当时最新观察相同时不重复追加，任一项相对最新观察变化时必须追加新版本，A→B→A 也保留后一次 A。持久化入口和数据库均拒绝周末日线；只有周一至周五且捕获时刻不早于该交易日上海时间 15:00 的完整日线才进入可靠 PIT 观察。工作日收盘前当日日线可以按原业务更新 `daily_bars`，但不得创建语义虚假的空观察批次或错误 `record_count`。成功的合格 PIT 捕获与当前态投影在同一事务内持久化；不得回填或伪造历史 `known_at`。
29. **2F 日终 knowledge-time 契约**：市场时区固定为 `Asia/Shanghai`；`decisionTime` 与 `knowledgeCutoff` 均为 `requestTradeDate` 当日最后一微秒。完整日线的最早合法知识时间固定为其 `tradeDate` 当日 15:00 上海时间；可靠观察必须是周一至周五，并满足 `firstObservedAt>=earliestDailyBarKnownAt`、`knownAt>=earliestDailyBarKnownAt`、`firstObservedAt<=knownAt<=recordedAt`、`tradeDate<=requestTradeDate` 与 `knownAt<=knowledgeCutoff`。周末日线直接拒绝；法定节假日仍由实际数据来源和后续正式日历能力治理。非交易请求日可使用此前最近有效交易日，但 cutoff 不移动。请求日期在未来或日终决策时点尚未到达时安全不可用。内容 Hash 不替代 knowledge-time、来源 revision 或数据版本证据。
30. **版本化上下文兼容边界**：只有团队规则版本 `1.4.0-stage-2f-strategy-backtest-v1` 显式选择 `AGENT_CONTEXT_2F_V1/BACKTEST_CONTEXT_V1`。旧 `create(symbol, tradeDate)` 入口及旧规则版本继续生成既有 `backtestContext.available=false`，不得改变 2B、2D-1、2E-1 的 contextSnapshot、contextHash、缓存键或结果。
31. **BACKTEST_CANONICAL_V1**：三个领域 Hash 固定使用 SHA-256、小写十六进制、UTF-8、Unicode NFC、对象字段名词典序、数组契约业务顺序、UTC `Z` 微秒时间及规范化十进制普通字符串；缺失字段与显式 `null` 不等价。`inputDataHash`、`strategyDefinitionHash`、`backtestResultHash` 各自只覆盖冻结白名单，数据库 ID、创建时间、日志与运行环境噪声不得进入。`dataVersion` 是独立的 PIT 模型、batch/dataset、所选观察版本和 source revision 对象，不得以 `inputDataHash` 冒充。
32. **冻结回测策略事实**：策略、引擎和参数版本分别为 `SMA20_NEXT_OPEN_RISK_EXIT_V1`、`BACKTEST_ENGINE_V1`、`BACKTEST_PARAMS_V1`。七项参数必须完整显式持久化；Java 是回测执行、稳定子区间和生产 Hash 的权威方。Python 不拉取行情、不访问数据库、不重跑策略或寻优，只按相同 canonical 契约校验并解释 Java 事实。
33. **STRATEGY_BACKTEST V1 安全边界**：可靠输入固定生成样本充分性、总收益、最大回撤、胜率与盈亏比、跨时间子区间稳定性五类 finding，并按冻结阈值计算 `[0,100]` score 与最高 80 的 confidence。DATA_QUALITY 阻断、上下文不可用、输入非法或交易样本不足均不得生成正常性能评分。STRATEGY_BACKTEST 永不产生正式 veto、投资建议、交易指令或收益承诺；POSITION_RISK 仍是唯一正式否决权，总控在公告风险与仓位风险未实现时仍保持安全不足结论。

## 可靠模拟持仓与 POSITION_RISK

34. **2H 当前模拟账户快照边界**：只有团队规则版本 `1.4.0-stage-2h-position-risk-v1` 选择 `AGENT_CONTEXT_2H_V1/PORTFOLIO_CONTEXT_V1`，且只读取默认模拟账户 `accountId=1`。Java 必须在同一个 `REPEATABLE_READ`、`readOnly=true` 事务中通过 Agent 专用 Repository 冻结账户、持仓、`PENDING_CONFIRM` 委托、请求日前权益快照、组合设置和请求日及以前最近本地 QFQ 收盘价；不得调用会结算、刷新行情、保存快照或写风险事件的 PortfolioService 路径。`requestTradeDate` 必须等于上下文生成时的上海自然日，周末可以评估当前状态；历史或未来日期安全不可用。
35. **portfolioContext 不提供历史 PIT 承诺**：2H V1 固定声明 `currentStateOnly=true`、`snapshotFrozenForTask=true`、`historicalPointInTimeGuaranteed=false`、`businessTablesReadOnly=true`。持仓缺少本地 QFQ 估值价或估值价超过七个自然日时整个上下文不可用；四至七日价格只降低 score/confidence。资金、市场价值、未实现损益、仓位权重、待买暴露和预计仓位均由 Java 从冻结明细重算并交叉验证。缺少历史权益指标不使上下文整体不可用，但 POSITION_RISK 必须进入 `PARTIAL`，按缺失项降低 confidence；无正式 veto 时 gate 为 `WARN`，存在正式 veto 时 gate 为 `BLOCKED`。该阶段不新增迁移，也不得伪造历史持仓版本。
36. **POSITION_RISK V1 正式否决顺序**：正式 veto 只可由 POSITION_RISK 按账户回撤、当日损失、最大持仓数、当前仓位权重、待买后预计权重、止损、移动止损的固定顺序生成；各 symbol 组内部按 symbol 升序。symbol 级 vetoCode 带稳定 symbol 后缀以满足既有 V5 唯一键；vetoId、reason、阈值、scope 和唯一 `PORTFOLIO_STATE` evidence 引用必须稳定。目标价达到只形成 warning finding，不得产生正式 veto；任何输出都不得成为交易执行指令。
37. **2H 总控优先级与兼容边界**：有效 portfolioContext 即使 DATA_QUALITY 为 `BLOCKED` 也必须执行 POSITION_RISK。存在正式 veto 时，总控固定为 `REJECTED_BY_VETO/BLOCKED/vetoed=true/score=0`，且完整引用全部 vetoId；无 veto 时 DATA_QUALITY 阻断仍形成 `BLOCKED_BY_DATA_QUALITY`；两者均未阻断时，因 ANNOUNCEMENT_RISK 尚未实现而保持 `INSUFFICIENT_DATA`。2H 不改变六个固定 run、总控非第七 run、旧 2B/2D-1/2E-1/2F profile、contextHash、缓存键或既有规则语义。

## 研究级公告事实与 ANNOUNCEMENT_RISK

38. **AKShare/CNINFO 只具有研究来源资格**：研究 Provider 固定为 `AKSHARE_CNINFO_RESEARCH_V1/AKSHARE_CNINFO_PROVIDER_V1`，AKShare 版本固定为 `1.18.64`。该来源的 assurance 只能是 `RESEARCH`，并固定 `formalEligible=false`、`pitVerified=false`、`revisionRelationshipGuaranteed=false`、`reportedPublishTimePrecision=DATE_ONLY`。它可以支持个人研究、风险提示、规则开发和从真实观察时点起的审计积累，但不能声明正式授权、历史绝对完整、精确首次公开时间、完整修订关系或自动交易资格，也不能解除 2D 正式证券状态来源和许可门禁。Python Provider Bridge 只调用 AKShare 公开函数并返回规范化原始记录；Java 仍是 observed/known time、校验、Hash、持久化和 Agent context 的唯一权威，Agent Rule Engine 不得调用 Provider、数据库、PDF 或外部网络。
39. **V10 append-only 公告观察模型与 knowledge-time**：V10 只新增不可变 `announcement_capture_batches` 与 `announcement_observations`，数据库触发器禁止 `UPDATE`、`DELETE`、`TRUNCATE`。完整成功且 0 条记录的批次是有效覆盖证据；部分失败批次只能审计，不能证明范围内无公告。公告发布时间只保存日期，不伪造日内时刻；Java 完整收到并验证 Provider 响应后冻结 `firstObservedAt`，且 `knownAt=firstObservedAt<=recordedAt`。历史公告今天首次观察时只能从今天的 knowledge-time 起可见。同一逻辑公告与最新版本 canonical 内容相同时幂等，内容变化及 A→B→A 都追加观察版本，不覆盖旧事实。
40. **公告来源身份与 ANNOUNCEMENT_CANONICAL_V1**：来源公告身份优先使用 CNINFO 明确公告 ID，编码为 `CNINFO:<id>`；没有明确 ID 时只允许对规范化 HTTP/HTTPS URL 生成 `CNINFO_URL_SHA256:<sha256>` 并标记 `URL_DERIVED`，禁止由标题、日期、symbol 或抓取顺序生成身份。`AKSHARE_CNINFO_RESEARCH_V1` 的 URL host 只允许 `cninfo.com.cn` 或其真实子域，拒绝相似后缀、userinfo 和非默认端口；该门禁由 Provider、Java canonical/摄取/context/响应校验、Python 规则输入校验和 V10 数据库共同执行。`ANNOUNCEMENT_CANONICAL_V1` 对来源、身份强度、证券、名称、标题、报告日期、日期精度、规范化 URL 和 assurance flags 使用冻结白名单、UTF-8 与 SHA-256 小写十六进制；Java 生成生产 Hash 和 observationVersion，Java/Python 通过固定输入、canonical 文本与外部固定预期值的黄金向量交叉验证。

## 确定性总控综合决策

44. **2I 只新增版本化总控，不新增上下文或第七个 run**：团队规则版本固定为 `1.4.0-stage-2i-chief-decision-v1`，总控契约为 `CHIEF_DECISION_V1`，权重契约为 `CHIEF_SCORE_WEIGHTS_V1`。精确 2I 规则版本复用与 2G 完全相同的 `AGENT_CONTEXT_2G_V1` 组合上下文；不得增加外层 contextSnapshot 字段、修改既有子 Context Schema、改变 2G contextHash、修改旧规则版本或创建 `CHIEF_DECISION` run。总控结果继续只进入 V5 `agent_decisions`，不新增 Flyway。
45. **2I 输入角色与固定权重**：DATA_QUALITY 只承担安全门禁、质量警告和综合 confidence 上限，其 score 不参与综合 score。MARKET_REGIME V1 的 score/confidence 权重均固定为 0，但必须处于当前 2D-1 契约允许的合法终态并继续进入 `sourceRunIds` 与顶层 findings/evidence。综合 score 和 confidence 只使用 TECHNICAL_ANALYSIS 25、STRATEGY_BACKTEST 35、ANNOUNCEMENT_RISK 20、POSITION_RISK 20，权重和精确为 100；不得按 confidence 重分配 score、在贡献者缺失时重新归一化或引入 finding/evidence 数量、summary 文本、错误文本、隐式指标或 LLM 输出。
46. **2I 决策优先级不可绕过**：任一合法 POSITION_RISK 正式 veto 最高优先，形成 `REJECTED_BY_VETO/BLOCKED/vetoed=true/score=0`，confidence 取 POSITION_RISK confidence；即使 DATA_QUALITY 阻断或其他 run 不足也不改变该优先级。无正式 veto 且 DATA_QUALITY 阻断时形成 `BLOCKED_BY_DATA_QUALITY/BLOCKED/vetoed=false/score=0`。前两者均不存在但 MARKET_REGIME、TECHNICAL_ANALYSIS、STRATEGY_BACKTEST、ANNOUNCEMENT_RISK 或 POSITION_RISK 任一不满足冻结可综合门禁时，必须形成 `INSUFFICIENT_DATA/NOT_APPLICABLE/0/0`，不得用残缺贡献者产生正常综合分类。非 POSITION_RISK veto 是非法响应。
47. **2I 综合计算与分类契约**：完整输入的 score 和原始 confidence 均按四个贡献者的固定权重求和后除以 100，并用非负整数 `HALF_UP` 取整。DATA_QUALITY 为 WARN 或 POSITION_RISK 为 PARTIAL 时，confidence 分别应用最高 50 的上限且分类最多为 `RESEARCH_ONLY`。公告与持仓风险只从冻结风险 finding code 的 severity 取 `INFO<WARN<HIGH<CRITICAL` 的最高值，不从 summary 重识别；公告来源覆盖和研究限制 finding 不等于发行人风险事件，不参与该最高风险值。DQ WARN、POSITION_RISK PARTIAL、风险 HIGH/CRITICAL、score<50 或 confidence<40 强制 `RESEARCH_ONLY`；只有全部人工复核门槛同时满足才能 `PASS_TO_MANUAL_REVIEW`，其余完整输入为 `WATCH`。`PASS_TO_MANUAL_REVIEW` 只表示进入人工研究复核。
48. **2I 输出只重用专业 findings/evidence**：`sourceRunIds` 必须按 DATA_QUALITY、MARKET_REGIME、TECHNICAL_ANALYSIS、STRATEGY_BACKTEST、ANNOUNCEMENT_RISK、POSITION_RISK 的固定顺序恰好包含六个 run；`vetoIds` 必须精确、稳定地等于顶层合法 POSITION_RISK veto 集合。final findings 与顶层 evidence 分别按相同六 run 顺序拼接，不创建总控 finding 或 evidence。summary 由决策、score、confidence 和固定研究边界模板生成，必须披露 MARKET_REGIME V1 权重为 0，且不得包含交易执行、仓位建议或收益承诺语言。
49. **Java 是 2I 最终复算与持久化权威**：Python 只执行无状态确定性总控规则，不访问数据库、网络，不修改事实或运行专业规则。Java 在持久化前独立复算六 run 身份、正式 veto/DQ/不足优先级、权重、`HALF_UP`、confidence 上限、最高风险 severity、finalDecision、gate、vetoed、score、confidence、summary、findings/evidence 顺序、sourceRunIds 与 vetoIds；任一不一致必须使 Agent 响应在既有事务边界内原子失败，不影响已经合法存在的行情、公告或模拟账户事实。2I 不改变 POSITION_RISK 唯一正式否决权，不产生投资建议、自动交易或真实账户能力。
50. **2I 专业 run 与总控持久化终态分层**：只对精确规则版本 `1.4.0-stage-2i-chief-decision-v1`，Java 必须显式依据 `finalDecision.decision` 决定总控终态，不得再只看专业 run 状态。`REJECTED_BY_VETO`、`BLOCKED_BY_DATA_QUALITY`、`RESEARCH_ONLY`、`WATCH`、`PASS_TO_MANUAL_REVIEW` 均表示确定性总控已经完成，task 与 decision 保存为 `COMPLETED` 并可进入既有完成缓存；只有最终 `INSUFFICIENT_DATA` 保存为 `task=PARTIAL/decision status=INSUFFICIENT_DATA` 且不得命中完成缓存。专业 run 的 `PARTIAL/INSUFFICIENT_DATA` 必须保留，旧 2B、2D-1、2E-1、2F、2G、2H 终态和缓存语义不变。

63. **QFQ V2 必须由 cutoff 前可见的 raw 与同日精确 factor 确定性重建**：`QFQ_AS_OF_ENGINE_V1` 的因子覆盖模式固定为 `DAILY_EXACT`。请求级日期使用 `requestEffectiveTradeDate/anchorTradeDate`，不得与因子字段 `factorEffectiveTradeDate` 混用；输入必须显式冻结 sourceCode 以及 raw、factor、calendar、corporate-action 四类来源身份。每根 raw bar 日期 `t` 只允许在同 Provider、正确证券/因子身份、同 `factorType` 且 `factorEffectiveTradeDate==t` 的精确自然键上选择 `knownAt<=knowledgeCutoff` 的资格优先、时间稳定 append-only 版本，锚点因子必须精确满足 `factorEffectiveTradeDate==anchorTradeDate`。V1 禁止 factor forward-fill、最近值替代、当前最新值补历史、从 QFQ 反推 factor、跨 Provider 拼接或对剩余窗口重新归一化；任一精确因子缺失或其 `knownAt` 晚于 cutoff 时返回 `PIT_FACTOR_UNAVAILABLE`。非 Provider verified 的 factor 修订只能由同 symbol/source、正确 action identity、相同 effectiveTradeDate 且不晚于当前因子可见时间的公司行动解释；无关日期或身份的 action 不得解除 `PIT_CORPORATE_ACTION_LINEAGE_UNAVAILABLE`。价格公式保持 `rawPrice(t,cutoff) * factor(t,cutoff) / factor(anchorTradeDate,cutoff)`；权威计算使用十进制 `BigDecimal`，除法 scale 16 `HALF_UP`，最终 OHLC scale 4 `HALF_UP`，volume、amount、turnover 不复权。Java 是 as-of 选择、QFQ、lineage 和 Hash 的唯一生产权威，Python 只验证固定结果向量和 Hash，不重算 QFQ。未来稀疏 effective-from step 因子必须建立独立 Provider 覆盖契约、证明生效区间并使用独立 engine 版本，不能由 V1 隐式推断。
64. **V2 设计不改变 2F V1，也不自行授权实施**：V9、`1.4.0-stage-2f-strategy-backtest-v1`、`AGENT_CONTEXT_2F_V1/BACKTEST_CONTEXT_V1`、旧 contextHash、缓存键和结果完全不变。未来 V2 必须使用独立 ruleVersion、contextProfile 和 Context Schema。Provider 中立的 TEST/DEMO 固定夹具、Mock Provider、四类事实、QFQ、2F V2 离线链路及保持禁用的 Adapter 骨架，可以在后续 3A-R3B-0 大阶段获得用户独立授权后先行实现；这不授予真实 Provider 资格，也不得发起 iFinD 调用。真实 Provider 字段映射、调用、Provider-backed 事实和资格声明仍必须通过里程碑启动门、用户激活、真实取证及许可审查。迁移版本、表名、API 和部署方式不在 3A-R3A 中决定。设计完成不等于 Provider 获批、V2 已实现、Day 002 获准、完整 3A 完成或 3B 开始。

## iFinD 试用里程碑启动治理

65. **iFinD 试用只由里程碑触发，不由日期触发**：iFinD 是由用户控制的有限 15 天试用窗口，启动不得绑定 `2026-08-31`、2026 年 8 月 31 日或任何其他固定日期。日历日期只能作为非权威临时估算，不能成为 `CURRENT_STATE.md`、`ROADMAP.md`、任务书、自动化配置或验收结论中的启动依据，也不得因预计日期临近而降低数据库、DTO、PIT、QFQ、Mock 闭环、证据采集或安全门槛。
66. **试用启动状态只有 PASS 或 BLOCKED**：正式标志只能是 `IFIND_TRIAL_ACTIVATION_GATE=PASS` 或 `IFIND_TRIAL_ACTIVATION_GATE=BLOCKED`。PASS 必须同时证明 Provider 中立接口与 DTO、四类 PIT 事实及隔离 PostgreSQL、append-only/幂等/A→B→A/cutoff、`DAILY_EXACT` QFQ 18 个黄金场景、2F V2 Mock、六智能体 Mock、EXPLICIT Mock Shadow、保持禁用的 iFinD Adapter 骨架和错误处理、函数/字段/证券/日期/调用预算清单、响应证据采集与脱敏工具、无待决重大数据库或 DTO 重构，以及用户可安排连续 15 天联调共 12 项条件全部通过；任一项缺失即为 BLOCKED。ChatGPT 在每个相关阶段基于实际 Git 提交和运行证据同步检查门禁，只有正式 PASS 后才建议用户开通，不得用预计日期或接近完成代替 PASS。
67. **iFinD 的申请、激活、调用和凭据由用户控制**：Codex 不得申请、激活、续期或自动调用 iFinD；试用前真实 iFinD 调用数必须为 0。只有用户看到正式 PASS 并亲自批准申请与激活后，才可开始连续 15 天集中接入与取证。用户名、密码、token、session、Cookie、认证头和完整敏感 URL 不得写入 Git、文档、日志、截图或测试夹具；凭据只能通过批准的安全运行时机制注入。试用调用必须受批准的函数清单与预算约束，禁止 scheduler、全市场遍历、无界自动重试和自动交易。
68. **有限试用不成为离线能力的单点依赖**：3A-R3B 必须先完成 Provider 中立离线闭环，再进行启动门、15 天真实取证和 Provider 资格判定。试用结束、额度耗尽或账号停用不得破坏 `SYSTEM_KNOWLEDGE_PIT`、Mock Provider、脱敏固定夹具和离线回归。最终资格只能依据真实证据与书面许可判定为 `PROVIDER_PIT_VERIFIED`、`PROVIDER_REVISION_UNVERIFIED`、`PROVIDER_REVISION_UNAVAILABLE`、`SYSTEM_KNOWLEDGE_PIT`，或许可不足/不批准接入；资格结论经 ChatGPT 对实际 Git 和运行证据验收并由用户批准前，不得恢复 Day 002，也不表示完整 3A 或 3B 已开始。

## Provider 中立 PIT 市场事实 V2 离线实现

69. **V2 实现使用独立版本和 V13，不改写任何旧契约**：3A-R3B-0 固定使用 `1.4.0-stage-3ar3b0-agent-team-pit-v2`、`AGENT_CONTEXT_3AR3B0_V2`、`BACKTEST_CONTEXT_V2`、`BACKTEST_CANONICAL_V2`、`PIT_MARKET_FACTS_V2`、`PIT_MARKET_FACTS_CANONICAL_V2` 与 `MARKET_FACT_PROVIDER_CONTRACT_V1`。V13 只前向新增 Provider 中立的 batch、observation、raw daily、adjustment factor、trading calendar 和 corporate action 事实，并扩展 TEST/DEMO Shadow 允许规则；V1 至 V12、V9 当前 QFQ、2F V1、旧 profile/contextHash/cache/result 均保持不变。V13 不回填 `daily_bars`、V9 或正常业务数据，只能先在随机隔离 Schema 验证；任务分支通过验收并由用户批准 merge 前不得视为集成能力。
70. **Provider 返回值与 Java 本地事实权威严格分层**：Provider 公共 DTO 可以表达四类上游事实、每类事实自身的稳定来源身份、capability、revision/snapshot/published/update time、许可、覆盖、单位、精度、完整性、错误和限流，但不得生成 `firstObservedAt`、`knownAt`、`recordedAt`、本地 datasetVersion、observationVersion 或 canonical Hash。后者只能由 Java 权威捕获、生成或验证。本地 UUID、时间、Hash 和版本不得提升为 Provider revision；未验证候选版本值不得进入合格 Provider metadata。raw 的 OHLC 必填，volume、amount、turnoverRate 可空且必须分别携带 `PRESENT_VERIFIED/PRESENT_UNVERIFIED/MISSING`、冻结单位和语义代码；PRESENT 必须有值、MISSING 必须为 null，明确 0 不等于缺失。QFQ 可保留这些非价格字段，但 2F V2 缺少合格 volume 时固定返回 `PIT_REQUIRED_MARKET_FIELD_UNAVAILABLE`。
71. **V2 事实链和 QFQ 必须完整或安全不可用**：四类事实均为 append-only；完整 semantic content hash 相同才幂等，业务值相同但资格、许可、providerSnapshotId、providerPublishedAt 或 providerUpdatedAt 变化仍必须追加，资格 A→B→A 保留第三个物理版本，并发捕获只允许一个合法链尾。as-of 查询必须显式接收 sourceCode、事实来源身份和 knowledgeCutoff，并对 calendar、raw、factor、corporate action 统一执行“先选版本、后验许可”：先在 cutoff 可见的同来源版本中按 revision qualification 优先级、knownAt、chainSequence、id 选出唯一语义版本，避免较晚低资格版本遮蔽已验证版本；再检查 usage qualification、local persistence、historical replay、backtest 和 Agent use。选中版本任一必要许可为 false 时固定返回 `PIT_USAGE_NOT_ALLOWED`，禁止在选版前过滤、回退旧允许版本或伪装成数据缺失；允许→禁止→重新允许必须保留三个版本和三个确定 cutoff 区间。batch 的 `providerDatasetVersion` 也只有 `PROVIDER_VERIFIED` 可以携带，其他 revision qualification 必须为 null。`QFQ_AS_OF_ENGINE_V1` 继续执行 `DAILY_EXACT` 和公司行动精确关联；任何 calendar/raw/factor/action lineage 缺失均返回稳定不可用结果，不得输出部分窗口。18 个黄金场景必须是含固定事实输入、时间、资格、预期输出、lineage 和 Hash 的可执行向量，由 Java 参数化运行引擎逐项断言，Python 只验证提交结果而不得重算第二套 QFQ。
72. **Mock 和 iFinD 骨架都不能取得真实来源资格**：3A-R3B-0 Mock Provider 仅允许 TEST/DEMO 合成固定夹具、`formalEligible=false` 和显式测试 profile，禁止网络并不得用于 Day 002。iFinD Adapter 默认 disabled，不安装 SDK、不创建真实客户端、不读取凭据；即使误配置 enabled，也必须在网络动作前以 `IFIND_TRIAL_GATE_NOT_PASSED` 失败。真实函数、字段、权限、额度、许可、revision 和 snapshot 均保持 `UNVERIFIED`，真实调用数保持 0。
